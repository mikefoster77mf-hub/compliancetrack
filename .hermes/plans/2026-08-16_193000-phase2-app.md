# Phase 2: ComplianceTrack App — Auth, Vendors, COIs, Dashboard, Reminders

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Build the actual ComplianceTrack SaaS app — user authentication, vendor management with COI tracking, PDF upload, dashboard, and email reminders — on top of the existing landing page + waitlist backend already live at `https://compliancetrack.app`.

**Architecture:** Single FastAPI service (already live on Render) extended with:
- Jinja2 templates for server-rendered app pages (login, signup, dashboard, vendors, COIs)
- Session-based auth via signed cookies (itsdangerous)
- PostgreSQL tables for users, vendors, COIs, reminder settings
- PDF storage in PostgreSQL bytea column (simple, no extra service needed for MVP)
- Resend API for email reminders (free tier: 3,000 emails/month) — or SMTP as fallback

**Tech Stack:** FastAPI, Jinja2, psycopg2, bcrypt, itsdangerous, python-multipart, Resend (or SMTP)

**Current state:** Phase 1 live — landing page at `/`, API at `/api/*` (health, db-check, db-items, db-seed, waitlist), PostgreSQL connected, `compliancetrack.app` + `www.compliancetrack.app` HTTPS live.

---

## Constraints & Decisions

- **Single service, same domain:** App pages coexist with landing page on `compliancetrack.app`. No separate subdomain needed.
- **Server-rendered HTML:** Jinja2 templates, not a JS framework. Keeps it simple for MVP.
- **Session auth, not JWT:** Signed cookies via itsdangerous. Simpler for server-rendered pages.
- **PDF storage in DB:** bytea column in COIs table. MVP-simple; can migrate to S3 later if needed.
- **Email via Resend:** REST API, free tier sufficient for MVP. Env var `RESEND_API_KEY`. Fallback to SMTP if user prefers.
- **No multi-user teams in Phase 2:** Single user (the GC). Team features deferred.
- **Existing landing page untouched:** Served as static files at `/`. App pages at `/login`, `/signup`, `/dashboard`, `/vendors`, etc.

## Database Schema

```sql
-- Users
CREATE TABLE IF NOT EXISTS users (
    id SERIAL PRIMARY KEY,
    email TEXT NOT NULL UNIQUE,
    password_hash TEXT NOT NULL,
    name TEXT NOT NULL DEFAULT '',
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Vendors
CREATE TABLE IF NOT EXISTS vendors (
    id SERIAL PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    name TEXT NOT NULL,
    email TEXT DEFAULT '',
    phone TEXT DEFAULT '',
    address TEXT DEFAULT '',
    notes TEXT DEFAULT '',
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- Certificates of Insurance (COIs)
CREATE TABLE IF NOT EXISTS cois (
    id SERIAL PRIMARY KEY,
    vendor_id INTEGER NOT NULL REFERENCES vendors(id) ON DELETE CASCADE,
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    pdf_data BYTEA DEFAULT NULL,
    pdf_filename TEXT DEFAULT '',
    insurance_type TEXT DEFAULT '',
    expiring_date DATE DEFAULT NULL,
    issued_date DATE DEFAULT NULL,
    notes TEXT DEFAULT '',
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- Reminder settings
CREATE TABLE IF NOT EXISTS reminder_settings (
    id SERIAL PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    days_before_expiry INTEGER NOT NULL DEFAULT 30,
    email_enabled BOOLEAN NOT NULL DEFAULT TRUE,
    updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

### Task 3: Auth API endpoints

**Files:**
- Modify: `backend/main.py` — add `/api/auth/signup`, `/api/auth/login`, `/api/auth/logout`, `/api/auth/me`

**Step 1:** `POST /api/auth/signup` — accept `{email, password, name}`, validate, hash password, insert user, return `{id, email, name}`. 400 if email already exists.

**Step 2:** `POST /api/auth/login` — accept `{email, password}`, look up user, verify password, on success set session cookie via `sig.sign(user_id)`, return `{id, email, name}`. 401 on failure.

**Step 3:** `POST /api/auth/logout` — clear session cookie, return `{status: "logged_out"}`.

**Step 4:** `GET /api/auth/me` — read session cookie, unsign, look up user, return `{id, email, name}` or 401 if not logged in.

**Session cookie details:**
- Set on login: `await response.set_cookie(key="session", value=sig.sign(str(user_id)), httponly=True, secure=True, samesite="lax", max_age=86400*30)`
- Read on protected requests: parse `request.cookies.get("session")`, `sig.unsign()`, look up user

Commit: `feat: add auth endpoints (signup, login, logout, me) with session cookies`

## Risks & Open Questions

1. **Email service:** Resend is recommended (simple API, free tier). User may prefer SMTP or another service. Decision needed before Task 14.

2. **PDF storage in DB:** bytea works for MVP but can bloat the database over time. If COI PDFs are large or numerous, consider migrating to Render Disk or S3 later. For now, COI PDFs are typically 1-5 pages (~100KB-500KB each), so even 1,000 COIs is under 500MB — well within the 15GB PostgreSQL storage.

3. **Reminder scheduling:** Background thread in FastAPI is simple but unreliable on Render (restarts kill it). Render cron jobs require checking if the Pro plan includes them. Alternative: check expiring COIs on each API request (lazy) — simpler but sends reminders late. Open question: does Render Pro support scheduled jobs?

4. **Session security:** Signed cookies are fine for MVP but not as secure as server-side sessions. If the SECRET_KEY is compromised, sessions can be forged. Rotate the key periodically. For MVP this is acceptable.

5. **Password reset:** Not included in Phase 2. If a user loses their password, they're locked out. Could add a simple "change password" flow later, or just let them sign up again (single-user app, so not critical).

6. **HTTPS-only cookies:** The `secure=True` flag on session cookies requires HTTPS. Render provides HTTPS, so this works in production. For local dev with mkcert, also works. If testing without HTTPS locally, set `secure=False` in dev (controlled by env var).
