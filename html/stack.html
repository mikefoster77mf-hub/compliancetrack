Stack Overview

Three containers, one private network, and a locally-trusted TLS certificate. This is the full stack that powers the site — from the reverse proxy in front to the database underneath.

N
Nginx TLS termination, reverse proxy, and static file serving. All HTTPS traffic hits Nginx first — it serves the HTML, CSS, and JavaScript, and forwards anything under /api/ to the backend. The HTTP-to-HTTPS redirect is handled here too. Podman · nginx:latest · Port 8443
F
FastAPI Backend The Python API server. Built with FastAPI and served by Uvicorn, it connects to PostgreSQL using psycopg2 and exposes a small set of REST endpoints under /api/. The /health endpoint checks the database connection, and /db-seed populates the database with sample data. Podman · Python 3.11 · Uvicorn · Port 8000
P
PostgreSQL 16 The relational database. Running on the official Alpine-based image, it stores all application data in a named volume that persists across container restarts. The backend connects to it over the compose network using environment variables for credentials. Podman · postgres:16-alpine · Port 5432

Network & Security

All three containers communicate over a private Podman network that's not exposed to the host. Only Nginx's ports (80 for HTTP, 8443 for HTTPS) are mapped to the host — the backend and database are reachable only from within the compose network.

TLS is handled by Nginx using a certificate generated by mkcert. The mkcert root CA is installed into the system trust store and the NSS database, so browsers treat the site as fully secure. The certificate covers localhost, 127.0.0.1, and ::1.

Resource Limits

Each container has CPU and memory limits set in the compose file. Nginx is capped at 0.5 CPU and 128MB memory, the backend at 1.0 CPU and 256MB, and the database at 0.5 CPU and 256MB. These limits translate directly into Kubernetes resource requests and limits when the stack is deployed to a cluster.

Reservations are set at half the limit for each service, ensuring the scheduler has a baseline to work with. This is the same pattern used in production Kubernetes deployments to balance packed scheduling with headroom for spikes.

Configuration

Environment variables — database credentials, hostnames, and connection parameters — are stored in a .env file that's excluded from version control. The compose file references this file with env_file, so secrets never end up in the manifest.

When the stack moves to Kubernetes, these variables will be split into a ConfigMap (non-sensitive config like DB_HOST) and a Secret (sensitive values like passwords). The application code already reads from environment variables, so the migration is transparent to the backend.
